## 二、流程详细说明

### 2.1 文档上传 → 自动生成工单 → 自动推送审批人

**这是系统最核心的业务链路。**

#### 步骤 1：员工上传文档

- 入口：`POST /kms/api/tickets/upload`（multipart/form-data）
- 员工上传文件，填写：
  - `module`：工单类型（doc_upload / doc_update / doc_delete）
  - `target_level`：文档密级 L0-L3
  - `owner_department`：归属部门
  - `extra_departments`：额外开放部门（可选）

#### 步骤 2：BLP 写权限校验

```python
# 不下写规则：员工只能写密级 >= 自己安全职级的文档
if doc_level < emp_security_level:
    raise "权限不足：不能向下写入低密级文档"
# 部门规则：员工部门必须等于文档归属部门
if emp_dept != doc_dept:
    raise "权限不足：文档必须归属本人所在部门"
```

#### 步骤 3：文档锁检查

```python
# 检查是否有在途工单
existing_lock = doc_lock.check_lock(doc_id)
if existing_lock:
    raise "文档已被其他工单锁定，请等待工单办结后再操作"
```

#### 步骤 4：暂存文件 + 生成内容哈希

```python
# 文件暂存到 staging 目录
staging_path = save_to_staging(upload_file)
# 计算内容哈希（防篡改）
content_hash = hashlib.sha256(file_content).hexdigest()
```

#### 步骤 5：自动创建工单

```python
# 系统自动创建两段式工单
ticket = {
    "ticket_no": generate_ticket_no(),
    "module": "doc_upload",
    "flow": "two_step",        # 两段式：审批即执行
    "applicant_id": emp.id,
    "payload": {...},
    "original_hash": payload_hash(payload),  # 提交时哈希
    "timeout_at": now() + timedelta(hours=72),  # 差异化超时
    "doc_id": doc_id,
    "status": "pending"
}
```

#### 步骤 6：自动匹配审批人（BLP + 部门）

```python
# 核心函数：auto_route_ticket(doc_level, doc_dept)
# 筛选条件：
#   1. security_level >= doc_level（满足 BLP 读规则）
#   2. department == doc_dept（同部门）
#   3. is_active == 1（在职）
#   4. id != applicant_id（不能自己审批自己）
candidates = acl.find_candidate_approvers(doc_level, doc_dept)
```

#### 步骤 7：获取文档锁 + 推送通知

```python
# 获取文档悲观锁
doc_lock.acquire_lock(doc_id, ticket_id, emp.id)
# 向候选审批人推送站内通知
for candidate in candidates:
    notify(candidate, f"新工单待审批: {ticket_no}")
```

#### 步骤 8：审批人审批

```
审批人看到工单 → 查看文档内容 → 通过/驳回
  ├── 通过：
  │   1. 核验哈希链：approved_hash == original_hash（防篡改）
  │   2. 系统自动执行入库（分块 + Embedding + 写入 documents/chunks）
  │   3. 释放文档锁
  │   4. 通知申请人
  └── 驳回：
      1. 填写驳回原因
      2. 释放文档锁
      3. 通知申请人
```

### 2.2 BLP 权限判定流程

```
                    ┌─────────────────┐
                    │  员工请求读文档   │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │ doc_level <=    │  ← 不上读
                    │ emp_security_   │
                    │ level ?         │
                    └────────┬────────┘
                      Yes ───┤─── No → ❌ 拒绝
                             │
                    ┌────────▼────────┐
                    │ emp_dept ==     │  ← 部门归属
                    │ doc_dept OR    │
                    │ emp_dept in    │
                    │ extra_depts ?  │
                    └────────┬────────┘
                      Yes ───┤─── No → ❌ 拒绝
                             │
                    ┌────────▼────────┐
                    │   ✅ 允许读取    │
                    └─────────────────┘
```

```
                    ┌─────────────────┐
                    │  员工请求写文档   │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │ doc_level >=    │  ← 不下写
                    │ emp_security_   │
                    │ level ?         │
                    └────────┬────────┘
                      Yes ───┤─── No → ❌ 拒绝
                             │
                    ┌────────▼────────┐
                    │ emp_dept ==     │  ← 严格同部门
                    │ doc_dept ?     │
                    └────────┬────────┘
                      Yes ───┤─── No → ❌ 拒绝
                             │
                    ┌────────▼────────┐
                    │   ✅ 允许写入    │
                    └─────────────────┘
```

**BLP 规则总结**：
- **读（不上读）**：`doc_level ≤ emp_security_level` — 低密级文档可以被高职级读，高密级文档不能被低职级读
- **写（不下写）**：`doc_level ≥ emp_security_level` — 高密级文档可以被低职级写（向上投稿），低密级文档不能被高职级写（防止降级泄露）
- **部门**：读 — 同部门或在额外开放部门列表；写 — 严格同部门

### 2.3 文档悲观锁生命周期

```
┌─────────────────────────────────────────────────────────────────┐
│                     文档悲观锁状态机                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  员工上传文档 ──→ check_lock(doc_id)                           │
│                    ├── 有锁 → 拒绝（"文档已在途变更"）           │
│                    └── 无锁 → acquire_lock(doc_id, ticket_id)  │
│                               │                                 │
│                               ▼                                 │
│                     ┌─────────────────┐                         │
│                     │  文档锁已持有    │                         │
│                     │  (uk_doc_id 唯一) │                        │
│                     └────────┬────────┘                         │
│                              │                                  │
│              ┌───────────────┼───────────────┐                  │
│              ▼               ▼               ▼                  │
│     审批通过执行      审批驳回        超时自动驳回                │
│     release_lock()  release_lock()  release_lock()             │
│              │               │               │                  │
│              └───────────────┼───────────────┘                  │
│                              ▼                                  │
│                     ┌─────────────────┐                         │
│                     │  文档锁已释放    │                         │
│                     │  可接受新工单    │                         │
│                     └─────────────────┘                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**关键约束**：
- `kms_doc_locks` 表的 `UNIQUE KEY uk_doc_id (doc_id)` 保证同一文档同一时刻只有一条在途变更工单
- 只读操作（问答查阅）不触发锁
- 超时驳回时强制释放锁

### 2.4 HR 同步失败兜底流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     HR 同步流程                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  定时/手动触发 ──→ 调用 HR 系统 API                             │
│                         │                                       │
│                    ┌────▼────┐                                  │
│                    │ 成功？   │                                  │
│                    └────┬────┘                                  │
│                  Yes ───┤─── No                                 │
│                  │      │    │                                  │
│                  ▼      │    ▼                                  │
│          upsert 到      │  记录失败日志                          │
│          kms_users      │  (kms_hr_sync_logs)                   │
│                  │      │    │                                  │
│                  │      │    ▼                                  │
│                  │      │  使用旧缓存数据兜底                    │
│                  │      │  (kms_users 上次同步快照)              │
│                  │      │    │                                  │
│                  │      │    ▼                                  │
│                  │      │  告警通知 L2+ 员工                    │
│                  │      │                                       │
│                  ▼      ▼                                       │
│              同步完成，记录日志                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**同步策略**：
1. **全量同步**：定时从 HR 拉取全量员工列表，upsert 到 KMS
2. **增量同步**：仅同步最近变更的员工
3. **手动触发**：L2+ 员工可手动触发一次同步
4. **失败兜底**：同步失败时使用旧缓存数据，保证系统可用性

### 2.5 工单超时自动驳回

```
定时扫描（每分钟）──→ check_timeout_tickets()
                         │
                         ▼
              查询 status='pending' AND timeout_at < now()
                         │
                         ▼
              对每个超时工单：
              1. status → 'timeout'
              2. 释放文档锁 release_lock(doc_id)
              3. 通知申请人："工单已超时自动驳回"
              4. 记录审计日志
```

### 2.6 文档版本管理与归档

```
上传同名文档 ──→ 计算 content_hash
                    │
               ┌────▼──────────────┐
               │ hash == 当前版本？  │
               └────┬──────────────┘
             Yes ───┤─── No
             │      │    │
             ▼      │    ▼
          跳过重复  │  归档当前版本：
             │      │  1. 旧 chunk → kms_archive_chunks
             │      │  2. 旧元数据 → kms_doc_versions
             │      │  3. 新文件入库为新版本
             │      │  4. version_no++
             ▼      ▼
          版本链完整，归档数据不参与 RAG 检索
```

### 2.7 API 网关全链路

```
外部请求 ──→ API Gateway Middleware
                │
                ├── 1. 请求 ID 注入（X-Request-ID）
                ├── 2. AppKey + 员工身份双层鉴权
                ├── 3. 速率限制（滑动窗口 60次/分钟）
                │      └── 超限 → 429 Too Many Requests
                ├── 4. 转发到路由层处理
                └── 5. 写入审计日志（kms_audit_logs）
                        └── 包含：操作人、动作、对象、IP、时间
```
