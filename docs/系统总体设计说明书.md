# 第一部分 宏观篇

## 1. 项目概述

### 1.1 建设背景与目标

本项目服务于银联商务两类互相隔离的业务目标：

1. **竞赛评测问答**：面向赛题评测的 `/chat` 接口，装载竞赛公开语料，要求回答准确、可追溯、低延迟；
2. **企业知识管理（KMS）**：面向企业内部的知识文档全生命周期管理，要求密级管控、流程内控、全程可审计，并对外部应用提供受控的知识服务。

两个目标共用同一套 RAG 内核（检索、重排、生成），但**数据、权限、入口完全隔离**，由此形成"单仓库、双服务"的总体形态。

### 1.2 双服务定位

| 服务 | 入口 | 端口 | 定位 | 认证 | 数据边界 |
|---|---|---|---|---|---|
| QA 问答服务 | `api.py` → `app/main.py` | **6341（固定）** | 赛题评测 `/chat` 接口 | 无（公开评测） | 仅装载竞赛公开语料 |
| KMS 知识管理系统 | `run_kms.py` → `scripts/service.py kms` | **6342~6350（默认 6342）** | 企业知识管理：权限、工单、审批、API 网关、多渠道接入 | PBKDF2 + JWT（员工）/ API Key（应用） | 企业数据，BLP 密级体系 |

**隔离是强制的，不是约定的**：两服务使用不同的 MySQL 数据库、不同的 FAISS 索引文件、不同的上传/文档目录，且路径之间不允许存在父子包含关系。启动器 `scripts/service.py` 在启动前完成端口绑定与部署值校验，**端口冲突即退出**，不自动换端口、不终止其他进程。KMS 服务上**不开放** `/chat` 赛题接口（访问返回 404），评测数据与企业数据不得混用。

### 1.4 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | Python 3.11 + FastAPI + uvicorn | 异步 Web 服务 |
| 前端 | Vue 3（组合式 API）+ Vite 构建 | 产物为静态 bundle，内网运行期零外链 |
| 结构化存储 | MySQL（pymysql + dbutils 连接池） | 业务数据、文档元数据、审计 |

| 网关单机状态 | SQLite（`data/gateway/state.sqlite3`） | 任务队列、回执、令牌撤销、会话 |
| 审计凭证 | JSONL 追加文件 | 与 MySQL 审计表双写，仅追加不修改 |
| Embedding 模型 | BAAI/bge-m3（1024 维） | 经 OpenAI 兼容 HTTP 接口调用 |
| Reranker 模型 | BAAI/bge-reranker-v2-m3 | 候选重排 |
| LLM | deepseek-ai/DeepSeek-V4-Flash | 答案生成 |

| 认证加密 | PBKDF2 密码散列 + 标准库 HS256 JWT；飞书 AES/SHA256 自研 | **零新增安全依赖**，核心安全决策点可逐行审计 |

**演示阶段零成本**：全部模型经 OpenAI 兼容接口调用，支持组委会 MaaS 与免费模型组双通道切换，无需支付外部服务费用。

## 2. 系统总体架构

### 2.1 分层架构总览

系统自顶向下分为五层，依赖方向严格单向（上层可依赖下层，下层不感知上层）：

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层    浏览器工作台(Vue3) │ 嵌入组件 │ 飞书/企微 │ 外部应用 │ MCP │
├─────────────────────────────────────────────────────────────┤
│ 网关层    gateway/                                          │
│           EnterpriseBoundary 中间件(限流/审计/请求ID/错误信封) │
│           routes_kms(文档/问答/治理) routes_tickets(工单)      │
│           routes_upload(批传) routes_embed(嵌入)              │
│           routes_bots(机器人) mcp/(MCP 服务面，默认关闭)        │
├─────────────────────────────────────────────────────────────┤
│ 业务域    kms/                                              │
│           security(认证) access_control(BLP/用户/审计)         │
│           lifecycle(生命周期) versioning(版本) org(组织树)     │
│           hr_sync/directory(HR与目录) recommend(推荐)          │
│           apps(应用Key) ratelimit(限流) oidc(SSO)             │
├─────────────────────────────────────────────────────────────┤
│ RAG 内核  app/  （QA 与 KMS 共用，不含任何权限概念）            │
│           document(解析/OCR/分块) rag(检索/重排/生成)           │
│           store(MySQL/FAISS/BM25) clients(模型客户端)          │
├─────────────────────────────────────────────────────────────┤
│ 存储层    MySQL(QA库/KMS库) │ FAISS索引文件 │ SQLite │ JSONL   │
└─────────────────────────────────────────────────────────────┘
```

**关键设计约束**：

1. **RAG 内核无权限概念**：`app/` 目录内 0 处部门/密级引用，全部权限过滤发生在网关层 `gateway/service.py` 的 `allowed()` 与 `current_contexts()`。权限不是检索器的附加参数，而是召回之后、生成之前的硬过滤。
2. **内核两侧共享**：QA 服务与 KMS 服务 import 同一份 `app/` 代码，但通过各自的环境变量装配出独立的存储实例，互不可见。
3. **唯一受控启动器**：两服务都必须经 `scripts/service.py` 启动，禁止绕过端口与数据隔离校验。

### 2.2 双服务隔离设计

| 隔离项 | QA（6341） | KMS（6342） | 校验位置 |
|---|---|---|---|
| 端口 | 固定 6341 | 6342~6350 | `config.py:validate_ports()` + `scripts/service.py:bind_socket()` |
| MySQL 数据库 | `.env` 的 `MYSQL_DATABASE` | `.env.kms` 的 `MYSQL_DATABASE`（不同库名） | `scripts/service.py:deployment_values()` |
| FAISS 索引目录 | `data/faiss/` | `data/kms/faiss/` | 同上（路径不得相互包含） |
| 上传/文档目录 | `data/uploads/` 等 | `data/kms/...` | 同上 |
| 认证 | 无 | JWT / API Key | — |
| CORS | 允许所有来源（无认证场景） | **显式列出，禁止通配符** | `config.py:validate_ports()` |

### 2.3 部署与启动控制

- **启动入口**：Windows `start_local.bat all` / Linux `start.sh all`；systemd 单元 `rag.service` / `kms.service`。
- **预检模式**：`python scripts/service.py qa --env .env --check`（不连接 DB/模型，仅校验配置）。
- **端口绑定**：启动器先 `bind_socket` 占用端口再拉起 uvicorn，冲突即报错退出，不抢占、不换端口。
- **启动一致性校验**：服务启动时比对 FAISS `ntotal` 与 MySQL `chunks` 行数，**不一致即拒绝启动**——宁可拒启也不在脏数据上静默给出错答案。
- **三段预热**：启动时对 Embedding / LLM（max_tokens=1）/ Reranker（top_n=1）依次发试探请求，消除 MaaS 冷启动，保证第一问延迟可测。
- **FAISS Unicode 补丁**：中文路径下 `faiss.serialize_index` 的回调签名问题由 `run_kms.py` 的 `_patch_faiss_unicode_paths` 以 `*args` 透传方式修复。

### 2.4 依赖策略

- 依赖版本一律使用 `>=` 范围约束，不用 `==` 锁死；
- 安全敏感逻辑（密码散列、JWT、消息加解密、签名校验）**全部使用 Python 标准库自研**，不引入第三方安全库，保证核心决策点可逐行审计；
- 配置全部来自 `.env` / `.env.kms` 环境变量，**代码中禁止硬编码任何密钥、密码、API Key**。

## 3. 知识加工流水线（RAG 开发思路）

本章回答"知识如何加工"。整体链路分为**入库（离线加工）**与**问答（在线检索生成）**两段，中间以三套存储（MySQL + FAISS + BM25）衔接。

### 3.1 全链路总览

```
【入库链路（文档 → 可检索知识）】
原始文件(只读，绝不改写)
  → 格式解析（pdf/docx/doc/txt/md/csv/json/xml/html/xlsx）
  → 逐页自适应 OCR 判定（纯扫描页/混合页/原生页）
  → 文本清洗与结构化（表格→Markdown、去重、错字清洗）
  → 分块（Chunker，300 字 / 重叠 80）
  → 向量化（bge-m3，1024 维，批量 32）
  → 三存储落地：MySQL chunks 表 + FAISS 索引 + BM25 倒排
  → 自动触发发布审批工单（双人审批）
  → 审批通过 → 热更新内存缓存与 BM25 → 进入可检索状态

【问答链路（问题 → 答案）】
用户问题
  → 问题归一化
  → 并行召回：FAISS 向量检索 ‖ BM25 关键词检索
  → RRF 融合排序
  → Reranker 重排（取前 8）
  → 父块扩展（small-to-big，仅前 3 块）
  → 【KMS 专属】权限硬过滤（不可见文档整块剔除）
  → 上下文组装（字数上限控制）
  → 两段式生成：逐字抽取步 → 作答步
  → 数字幻觉校验 → 拒答兜底
  → 输出答案 + 来源列表（KMS）/ 纯答案（QA 评测）
```

### 3.2 文档解析与逐页自适应 OCR

PDF 解析不做文档级的"扫描件/原生件"二分类，而是**每页独立判定**，解决"文字页内嵌大图导致内容遗漏"的实际问题：

| 页面类型 | 判定条件 | 处理方式 |
|---|---|---|
| 纯扫描页 | 文本层为空 | 整页调用 PaddleOCR-VL 识别 |
| 混合页 | 文本层非空，且单张嵌入图占页面面积 > 15% | 保留文本层，对图片区域补 OCR，结果逐行去重后合并 |
| 原生页 | 文本层非空且无大图 | 直接提取文本层，不调用 OCR（省算力、保精度） |

配套的 OCR 质量防线（`app/document.py`）：OCR 退行检测（`_ocr_degenerate`）、与 pdfplumber 结果相似度比对（`_ocr_vs_pdfplumber_similar`）、多策略重试（`_ocr_strip_with_retry`）、提示词回显剥离（`_strip_prompt_echo` / `_strip_ocr_echo`）。针对财务报告类表格页曾出现的"数字粘连、序号与数值堆叠"问题，设有专门的表格修复与数字清洗规则（千分位误判修复、相邻数字粘连拆分）。

### 3.3 文本清洗与结构化

入库前对文本做多轮"卫生处理"，全部在内存中完成，**源文件只读不改写**：

- **表格结构化**：DOCX/XLSX/PDF 表格统一转换为 Markdown 表格（`_rows_to_markdown` / `_table_to_markdown`），保留行列语义，使"前三季度主营业务收入"这类表格问答可被命中；
- **重复内容清理**：连续行去重、循环行检测剔除（页眉页脚类）、行内重复压缩、塞满段落展开；
- **OCR 形近错字清洗**：`app/typo_clean.py` 采用数字保护式替换，修复"扫描件转 Word"文字层污染（原图丢失无法重 OCR 的存量文档），可通过 `CLEAN_OCR_TYPOS=0` 关闭；
- **元数据提取**：从文件名/内容提取标题、作者、语言等治理元数据，写入 `documents` 表。

### 3.4 分块策略

- **参数**：`CHUNK_SIZE=300` 字符、`CHUNK_OVERLAP=80`（QA 与 KMS 完全一致，保证两库分块行为可对照）；
- **递归切分**：`_recursive_split` 按段落→句子→硬切的优先级递归，尽量在语义边界断开；
- **父子块结构**：小块用于精确召回，大块（父块）用于提供上下文；`split_with_positions` 记录每块在原文的位置，支撑后续的父块扩展与重叠合并；
- **结构化手册特殊处理**：章节标题作为前缀注入每个正文 chunk，避免"命中同文档错误段落"的问题。

### 3.5 向量化与三套存储

| 存储 | 内容 | 作用 |
|---|---|---|
| MySQL `chunks` 表 | chunk 全文 + faiss_id + 页码/章节 + text_hash | 事实源（向量索引可据此重建） |
| FAISS 索引文件 | 1024 维向量（IndexIDMap2 包装 IndexFlatIP） | 语义相似度召回，支持按 ID 精确删除 |
| BM25 倒排（内存） | jieba 分词后的词项倒排 | 关键词/专有名召回，弥补向量对精确词的不敏感 |

- Embedding 客户端带 LRU 缓存，批量 32 条/次，文本先经 `_clean_text` 去噪再送模型；
- **Indexer 与 Retriever 共享同一个 VectorStore 实例**（`kms/routes.py` 单例），避免两侧内存态不同步导致的索引互相覆盖、新向量丢失；
- FAISS 删除操作校验实际删除数量并记录告警日志，防止向量静默删除造成存储与索引不一致。

### 3.6 检索链路

`Retriever.retrieve` 的执行顺序：

1. **问题归一化**：全半角、空白、标点规范化；
2. **双路召回**：向量检索（`TOP_K_RETRIEVE`）与 BM25 检索（`BM25_TOP_K=20`）并行；
3. **RRF 融合**（`_rrf_fuse`）：对两路结果按排名倒数融合，避免单路偏好；
4. **安全重排**（`_safe_rerank`）：Reranker 模型对候选重排，取 `TOP_K_RERANK=8`；重排服务不可用时降级为融合序；
5. **父块扩展**（small-to-big）：仅对前 3 个块扩展其父块窗口，防止上下文膨胀；
6. **低质块剔除与重叠合并**：垃圾块判定（`_is_junk` / `_chunk_is_garbage`）、重叠去重（`_dedup_overlap`）、断行重排（`_reflow_broken_lines`）；
7. **按文档排序组装**（`_order_contexts_by_document`），控制总字数（`MAX_CONTEXT_CHARS`）。

**性能关键**：chunk 文本在启动时全量预载内存（`ChunkCache`），单次问答链路中**没有 MySQL 查询**，只访问 FAISS + 内存 + 模型接口。

### 3.7 两段式生成与幻觉防控

- **两段式生成**（`_generate_two_stage`）：第一步"抽取步"只允许从参考资料**逐字抄写**相关原句，禁止概括改写；第二步"作答步"仅基于抄出的句子组织答案。从机制上压缩小模型脱离上下文自由发挥的空间。QA 评测侧当前以 `ENABLE_TWO_STAGE=0` 关闭（追求直接答案与速度），KMS 侧启用。
- **数字幻觉校验**（`_has_number_hallucination`）：答案中出现而参考资料中不存在的数字会被识别，触发重生成或拒答——专治财务类问答的"编造数字"。
- **拒答判定与兜底**（`_is_refusal` / `_extractive_answer`）：模型拒答或证据不足时，KMS 受限用户走**抽取式降级**（直接摘录最相关原句），不走自由生成路径，防止绕过权限过滤。
- **KMS 权限前置**：受限用户召回量 ×3 取候选 → `allowed()` 逐块过滤 → 再截取重排前 N 块；**在 LLM 调用前再次校验文档可见性**（流式输出无法撤回，必须先过滤后生成）。

### 3.8 一致性与热更新

- **启动一致性校验**：FAISS 向量数 = MySQL chunks 行数才允许服务就绪（`/kms/api/audit/ingest-status` 可查看 `faiss_mysql_consistent`）；
- **发布后热更新**：文档审批通过后调用 `_hot_update_caches()`，在不重启服务的前提下刷新 chunk 内存缓存与 BM25 索引，新文档立即可被检索；
- **重建纪律**：全量重入库脚本（`reingest_all.py` 等）要求先停服务，避免 FAISS 文件并发争用；重入库前自动全量导出 JSON 快照 + FAISS 副本，可整体回退。

### 3.9 QA 与 KMS 检索参数差异（设计使然，非缺陷）

| 参数 | QA（6341） | KMS（6342） | 差异理由 |
|---|---|---|---|
| TOP_K_RETRIEVE | 30 | 20 | 评测求召回率；企业求精度与延迟平衡 |
| TOP_K_RERANK | 8 | 8 | 一致 |
| MAX_CONTEXT_CHARS | 4000 | 3000 | 企业侧答案要求更收敛 |
| ENABLE_TWO_STAGE | 0（关） | 启用（默认） | 评测求快；企业求准 |
| LLM_TEMPERATURE | 0.1 | 0.3 | 评测求确定性 |
| LLM_MAX_TOKENS | 1024 | 512 | 评测题有列举类长答案 |
| 分块/向量参数 | 300/80、bge-m3、1024 维 | 同左 | **完全一致** |

# 第二部分 安全与流程篇

## 4. 文档权限管理

### 4.1 角色模型：只有"员工"一类主体

系统中**不存在"管理员"角色**。所有账号均为在职员工（一人一个唯一工号，工号格式 2026+四位数字，初始密码为工号），权限差异完全由**组织属性**派生：

| 身份 | 来源 | 能做什么 |
|---|---|---|
| 员工 | HR 数据同步（唯一基础身份） | 问答、浏览目录、上传文档、发起各类工单；能读什么由 BLP 决定，变更须过双人审批 |
| 运营审计 | HR 岗位类别 `auditor`（环境变量兜底指定） | 员工全部能力 + 审计类只读接口 + 应用绑定管理；**对业务内容不额外授权** |

**为什么刻意不设管理员**：审批权若来自"管理员身份"，谁当管理员谁就能批一切，审批就成了身份特权而非岗位责任。本系统审批权由"部门 + 安全职级 + HR 涉密资格"派生，判定入口唯一（`access_control.approver_candidates()`）。临时提权功能已彻底移除（对应端点固定返回 404），人员账号、部门、职位、安全职级全部从 HR 数据表**单向只读导入**，本系统不维护人事主数据。

### 4.2 两个正交维度：密级 × 部门

| 维度 | 取值 | 作用 |
|---|---|---|
| 员工安全职级 | L0 / L1 / L2 / L3 数字编号 | BLP 模型中"人"的刻度 |
| 文档密级 | 0~3 四级（对外中文表述：公开/秘密/机密/绝密） | BLP 模型中"物"的刻度 |
| 归属部门 | 具体部门 或 哨兵值 `*`（不限） | 部门隔离；`*` 只放开部门维度，**不是放开隔离本身** |

> 术语纪律：员工侧一律使用 L0~L3 数字职级编号；文档侧使用中文密级称谓。二者严格区分，不混用。

`*` 哨兵的精确语义：L2 员工可以读"不限部门"的 L2 文档，但仍不能读**别部门限定**的 L2 文档——放开的是部门维度，密级维度照常约束。

### 4.3 BLP 读写规则与 fail-closed

判定函数 `access_control.can_read_doc / can_write_doc` 是权限的**单一事实源**：

- **读（不上读）**：`文档密级 ≤ 员工职级`，且满足部门条件（同部门 / 在文档 `extra_departments` 额外授权列表 / 组织路径继承范围内）；
- **写（不下写）**：`文档密级 ≥ 员工职级`，且严格同部门（写下层被拒）；
- **fail-closed 三原则**：无密级登记的文档一律判不可读；归属部门为空串（未登记）的文档谁都不可见；"不限部门"必须使用独立哨兵 `*`，空串不等于不限。

**列表与问答同源**：文档列表走 `visible_documents_sql()`，问答走 `current_contexts()`，二者最终都汇入 `can_read_doc()`。若不同源，会出现"列表看不到、问答搜得到"——那等于把权限做成了界面装饰。

### 4.4 组织继承与额外授权

- **组织树**：`kms_org_nodes` 表以 `parent_id` 自引用 + `org_path` 前缀路径存储组织架构；部门经理自动拥有其**所有下级组织节点**文档的访问权限，权限判定基于 `org_path` 前缀匹配，无需逐文档配置；
- **额外授权部门**：文档可配置 `extra_departments`，允许指定部门跨部门访问；跨部门访问**同时满足 BLP 规则与部门授权**，权限取两者交集，不放大；
- **RAG 组织上下文注入**：每次问答请求自动将当前用户的组织信息、安全职级、可见组织范围、回答策略注入系统提示词，回答优先使用用户所属组织范围内的资料。

### 4.5 发布的四重闸门

一篇文档要被检索到，必须**同时**满足四个条件：

```
status = 'published'           （业务状态）
lifecycle_state = 'published'  （生命周期状态）
publication_approved = 1       （双人审批产物）
未过期（expires_at 未到期）
```

**草稿不进检索**。真正的暴露门槛是发布审批，而不是上传动作——上传成功只意味着文档进入草稿态。

### 4.6 审批人自动匹配

工单审批人由系统自动指派，前端**不提供人工选择审批人入口**。候选条件（同时满足）：

1. 与文档同归属部门，或文档归属为 `*`；
2. 安全职级 ≥ 文档目标密级；
3. **HR 涉密准入通过**：在职/试用 + 正式员工 + 已签保密承诺 + 背景审查通过；
4. 排除申请人本人（A/B 分离，不能自批）。

第 3 条的理由：让没有涉密资格的人去审批一篇他无权接触的文档，形式上是双人审批，实质是单人决定。审批人资格校验按工单的**目标态**（目标密级 + 目标归属部门）执行，与指派口径一致，避免"指派后无法审批"的死锁。

### 4.7 认证与令牌体系

- **登录**：工号 + 密码（PBKDF2 散列存储），失败 5 次锁定 5 分钟；
- **令牌**：标准库自研 HS256 JWT，载荷含 sub/emp/role/level/dept/jti；签名密钥来自 `data/kms_secret.key`（环境变量 `KMS_SECRET_KEY` 优先）；
- **实时查库**：令牌虽无状态，但每次请求实时查库校验用户在职状态——**停用账号立即生效**；
- **令牌撤销**：改密/停用触发用户级全量撤销（SQLite `revoked_tokens` / `user_revocations` 表按 jti 拦截）；
- **SSO 单点登录**：标准 OIDC 流程（授权端点 → 登录页 → 一次性授权码 60 秒 → 令牌端点），HTTP-only SameSite=Lax 会话 Cookie，state 参数防 CSRF；通过 `OIDCProvider` 抽象支持内置模拟与外部 OIDC 平台（JWKS 公钥 RS256 校验，严格校验 iss/aud/exp），生产环境可直接对接 AD/LDAP 身份提供商；
- **目录同步可插拔**：`DirectoryAdapter` 抽象支持 seed / LDAP / AD / HR API 四种数据源，环境变量 `KMS_DIRECTORY_SOURCE` 切换，缺失依赖时抛出明确错误，不静默降级；
- **HR 同步**：单向只读 upsert，行哈希增量对账保持数据一致性，同步失败用旧缓存兜底，全部同步动作留有历史记录。

### 4.8 审计体系：三处存储 + WORM + 哈希链

| 审计面 | 载体 | 内容 |
|---|---|---|
| KMS 业务审计 | MySQL `kms_audit_logs` | 登录、文档操作、工单流转等，支持按时间/用户/动作/对象/结果多维筛选与 CSV 导出（导出动作本身也留痕） |
| 对外网关审计 | MySQL `kms_gw_audit` + JSONL 文件双写 | 渠道、应用、外部身份、员工工号、状态码、耗时 |
| 工单防篡改 | `kms_tickets.original_hash` / `approved_hash` | 建单时计算申请内容规范化 JSON 的 SHA-256，审批时复算比对，不一致即标记篡改拒绝执行 |

所有删除/恢复操作的快照哈希写入 **WORM 审计日志**（仅追加、不可修改、不可删除），满足涉密文档销毁的审计追溯要求。三个审计数据集互相独立、不可互相替代。

## 5. 文档全生命周期与版本治理

本章回答"文档更新及版本冲突如何解决"。

### 5.1 生命周期状态机

文档采用标准状态机：**草稿 → 审核 → 发布 → 归档 → 销毁**。所有状态转换均有前置校验并记录流转历史；文档上传默认进入草稿态，必须经工单审批才可正式发布。`kms/lifecycle.py` 提供状态读取、转换校验、软删除、过期检查等能力。

### 5.2 两段式工单流程（申请 → 审批即执行）

所有高风险操作（上传、更新、删除、恢复、密级调整、批量操作）**只能**通过工单流转，外部应用也不得直接写入底层存储：

```
① 建单：任何在职员工发起（须有归属部门）
        → 系统按 4.6 节规则自动匹配审批人
        → 写入 original_hash 与 doc_references 文档快照
        → 占用文档悲观锁（同 doc_id 仅一条在途工单）
② 审批：审批人复核（可在线查看文档内容/下载原文）
        → 校验哈希链、复核审批人资格
        → 通过即由系统自动执行（无独立执行人角色）
③ 执行：按模块分发到对应执行器
        → 成功后清理 FAISS 向量、热更新缓存、发送站内通知
④ 超时：扫描器自动驳回并释放文档锁
```

**关键机制**：

- **哈希链防篡改**：`original_hash`（建单）→ `approved_hash`（审批），payload 被改即拒绝执行；
- **文档悲观锁**：同一 `doc_id` 同一时刻只允许一条在途变更工单，从源头消灭并发变更；
- **差异化超时**：上传 72 小时、更新 48 小时、删除 24 小时、恢复 48 小时，超时自动驳回释放锁；
- **建单快照**：`doc_references` 保存建单时的文档元信息 JSON 快照——文档被物理删除后，审计仍可见"当初操作的是什么"；快照机制上线前的历史工单由详情接口实时查询兜底展示；
- **通知闭环**：工单待审批、通过、驳回均产生站内通知（`kms_notifications`）。

### 5.3 文档更新与新版本入库

同名文档上传即产生新版本，规则如下：

1. 旧版本自动归档（`kms_doc_versions` 记录，版本号自增），检索默认**只召回当前版本**，历史版本不占检索通道——从机制上避免 RAG 同时召回新旧两版矛盾内容；
2. 基于 `content_hash + version_no` 的**乐观锁**防并发冲突；内容完全相同的上传自动去重，不产生虚版本；
3. 新版本同样自动触发发布审批工单，审批通过后才替换检索面；
4. **版本回滚**采用"旧源文件重新 ingest 生成新版本"的方式，保证 FAISS、chunks、content_hash 三者一致——而不是简单切换版本指针（指针切换会留下索引与存储不一致的隐患）。

### 5.4 版本冲突防控小结

| 冲突场景 | 防控机制 | 实现位置 |
|---|---|---|
| 两人同时改同一文档 | 文档悲观锁：同 doc_id 仅一条在途工单 | `routes_tickets._create_ticket` |
| 工单审批中途 payload 被改 | 哈希链比对，不一致拒绝执行 | `_payload_hash` / `approve_ticket` |
| 新旧版本同时被检索 | 旧版本归档，检索只认当前版本 | `versioning.py` + 检索过滤 |
| 并发上传同内容 | content_hash 去重 + 乐观锁 | `versioning.record_version` |
| 工单挂死占用文档 | 差异化超时自动驳回释放锁 | `_sweep_timeouts` / `_settle_timeouts` |
| 索引与库存储不一致 | 启动一致性校验，不一致拒启 | `app/rag._repair_consistency` |

### 5.5 删除、回收站与恢复

- **物理删除 + 快照留痕**：涉密文档销毁要求不留残体，删除为物理删除；删除动作通过工单快照哈希写入 WORM 审计，满足可追溯；
- **30 天回收站**：删除后进入回收站保留 30 天，宽限期清扫器自动清理逾期项；
- **恢复工单**：恢复同样遵循双人审批两段式规则，避免误批导致不可逆损失；
- **原子化执行**：批量删除使用数据库 SAVEPOINT，要么全部完成要么全部回滚；执行前完成三项前置校验——批量预查文档存在性、复核申请人对每篇文档的管理权限、校验删除原因字数（2~500 字）；
- **孤儿清理**：删除文档连带清理 `kms_doc_levels` 等关联表，不留悬空引用。

## 6. 对外服务体系（如何为不同应用提供服务）

### 6.1 六种服务方式总览

| # | 方式 | 入口 | 身份凭证 | 适用场景 |
|---|---|---|---|---|
| 1 | 标准 REST API | `/gw/api/v1/...` | 应用 API Key（`X-API-Key`） | 外部系统后端集成 |
| 2 | 嵌入式 Web Component | `/gw/api/v1/embed/*` | 宿主 BFF 持 Key + 短期员工令牌 | 业务系统页面内嵌问答 |
| 3 | 办公 IM 机器人 | `/gw/api/v1/bots/feishu|wecom/callback` | 平台签名 + 身份绑定 | 飞书/企业微信私聊问答 |
| 4 | MCP 服务 | `/gw/api/v1/mcp*` | API Key 或员工 JWT | AI Agent 工具调用 |
| 5 | OIDC 单点登录 | `/kms/api/auth/sso/*` | 授权码 + 会话 Cookie | 企业统一认证集成 |
| 6 | 评测直连 API | 6341 端口 `/chat` | 无（公开评测） | 竞赛评测 |

**两类服务身份**：员工（JWT，工号+密码登录）与应用（API Key，仅存 SHA-256 哈希）。应用绑定密级上下界，其可读范围**同样受 BLP 约束**——不存在"应用是特权身份"。每个应用独立密钥、独立限流配额、支持密钥轮换，全部调用留存审计。

### 6.2 标准 REST API（应用 API Key）

- 应用在 KMS 注册后获得 `app_id` + API Key（服务端只存哈希，泄露数据库不泄露密钥）；
- 每个应用绑定可访问的**密级上下界**，检索结果按应用可见范围过滤；
- 双层鉴权（Key 校验 + BLP 过滤）+ 按应用独立限流 + 全量审计（`kms_gw_audit`）；
- 应用默认只读；任何文档变更只能发起工单，不能直接写入。

### 6.3 嵌入式 Web Component

```html
<script type="module" src="/static/knowledge-widget.js"></script>
<enterprise-knowledge endpoint="/kms/api/chat"></enterprise-knowledge>
```

安全约定（由架构测试强制）：组件只持**短期员工令牌**（由宿主 SSO 会话经 `tokenProvider` 注入）；**不接触应用 Key**（`X-API-Key` 必须由宿主 BFF 持有，`examples/embed_bff.py` 提供同源 BFF 示例）；仅允许同源 endpoint，禁止把令牌转发到外部站点；回答按不可信数据渲染（安全 Markdown + 不执行其中指令）。

### 6.4 办公 IM 机器人（飞书 / 企业微信）

- 采用**企业自建应用双向消息**模式（非单向 webhook 群机器人），支持员工私聊问答与身份权限绑定；
- 三层安全校验：AES 消息加解密 + Verification Token 校验 + SHA256 事件签名校验，自动响应平台 URL 验证 challenge；
- **身份绑定**：外部平台账号必须通过 `/kms/api/admin/bot-bindings` 绑定员工工号；未绑定用户的消息一律不回复，仅记录审计日志；
- 仅处理私聊文本消息；群聊、非文本消息静默忽略；回调消息异步入队（SQLite 任务队列去重 + 有界重试），回执表支撑反馈归属校验。

### 6.5 MCP 服务（默认关闭）

- 面向 AI Agent 的 JSON-RPC 服务面，提供 8 个白名单工具（`search_knowledge` / `ask_question` / `get_document` / `list_documents` / `get_recommendations` / `submit_feedback` / `submit_knowledge_request` / `get_app_usage`）；
- 双模认证：应用 API Key 或员工 JWT；注入防护（不可信内容包装清洗）；逐工具限流与指标计数；
- SDK 能力面由架构测试自动校验——MCP 新增工具而前端 SDK 未同步时测试失败，复用契约不会静默腐烂。

### 6.6 OIDC 单点登录

见 4.7 节。对外价值在于：业务系统可用标准 OIDC 协议将员工认证托管给 KMS（或经 KMS 对接企业 AD/LDAP），嵌入组件与机器人都以此获得员工身份。

### 6.7 评测直连 API（竞赛规范，勿改）

```
POST /chat        （兼容 JSON / form-data / ?question= 三种入参）
请求: {"question": "xxx"}
响应: {"answer": "xxx"}
```

只返回 answer，不带引用来源；KMS 服务上不开放此接口。

### 6.8 网关安全机制

- **EnterpriseBoundary 中间件**：请求体体量上限、请求 ID 注入全链路日志、统一错误信封；对 SSE 流式响应豁免整包缓冲（审计在流结束后补记）；
- **三套独立限流**：按来源 IP、按嵌入应用、按 MCP 员工工号，跨实例固定窗口计数（MySQL 持久化）；
- **出网开关**：`GW_MODEL_EGRESS_ALLOWED` 控制是否允许经网关调用外部模型；
- **指标保护**：`/metrics` 仅运营审计可读，避免向外部暴露调用画像。

## 7. 管理系统功能（前端工作台）

### 7.1 前端架构

- **Vue 3 单页工作台**（组合式 API），Vite 构建（`vite.app.config.js`）输出到 `kms/web/dist-app/`，由 `run_kms.py` 的 `/static` 路径服务；
- **金融内网零外链红线**：所有依赖构建期内联，产物不请求任何公网资源；全部静态资源响应带 `Cache-Control: no-cache`，杜绝浏览器缓存旧代码；
- **单一客户端复用**：工作台（构建期 `@kms` 别名）、嵌入组件（运行期直引）、MCP 控制台三方共用 `kms-client.js` SDK——后端新增能力只需在 SDK 加一个方法，消费方同时获得；
- **工程化配套**：ESLint flat config、hidden sourcemap（可调试不泄露源码）、组件级错误边界（`onErrorCaptured`）、权限显隐统一走 `policy.js` 纯函数镜像（真正判定永远在服务端）。

### 7.2 功能栏目明细

| 栏目 | 视图 | 功能 |
|---|---|---|
| 仪表盘 | DashboardView | 统计总览、检索参数面板（基础只读信息全员可见） |
| 文档库 | DocumentsView | 文档列表（服务端分页 20 条/页）、详情、版本列表、回滚、上传（密级/部门固定下拉） |
| 智能问答 | ChatView | 多会话问答（session_id 后端生成）、SSE 流式输出、来源展示、反馈 |
| 工单中心 | TicketsView | 三互斥 tab（见 7.3）、详情弹窗、在线查看文档内容、下载原文 |
| 个人中心 | PersonalView | 个人信息、改密、我的统计、通知 |
| 系统状态 | SystemView（仅运营审计） | 服务健康、入库一致性、指标 |
| 管理视图 | AdminView（仅运营审计） | 用户/层级/部门、审计查询导出、HR 同步、应用管理 |

**交互纪律**：所有可枚举字段一律固定下拉/滑块（禁止自由文本）；提交按钮统一加载态防重复提交；员工列表、审计筛选等一切展示列表按工号升序；上传区部门选项在用户信息加载完成后重渲染。

### 7.3 工单中心：三个互斥 tab

| tab | 内容 | 口径 |
|---|---|---|
| 我的申请 | 我发起的**进行中**单据 | 申请人 = 我 且 非终态 |
| 待我审批 | 待我审批的工单 + 待我审批的发布申请 | 审批人 = 我 且 待处理 |
| 已完成 | 全部终态记录（工单 + 已决策发布申请） | 终态 |

三类单据严格互斥，同一单据只出现在一个 tab 中；所有条目均可展开完整详情。发布申请详情弹窗提供**文档内容查看**（分块预览）与**原版下载**，审批人可凭此完成审阅——权限判定遵循 BLP 规则，不放大访问范围。

### 7.4 问答与流式输出

- 流式问答采用零侵入方案：复用 `/kms/api/chat` 端点加 `?stream=true` 查询参数，不改动原非流式路径；
- SSE 事件格式分两阶段：先逐段输出文本片段，最后输出含完整答案、来源列表、会话 ID 的 `done` 事件，与非流式返回结构对齐；
- LLM 调用前再次校验文档可见性（流式内容无法撤回）；前端处理 TCP 拆包，流结束后手动 flush 缓冲区确保完整解析 done 事件；
- 会话历史的 `session_id` 一律由后端生成，会话归属经 `kms_chat_owners` 表校验，防止伪造会话访问他人历史。

### 8.7 模块依赖关系与循环规避

依赖图为**有向无环图（DAG）**，核心内核对业务域零反向依赖。关键边：

- `kms/routes.py ← app/{rag, store} + config`：KMS 侧唯一的 RAG 接入点；
- `gateway/service.py ← kms/{access_control, security, org, routes} + app/rag`：权限过滤在网关层收口；
- `kms/access_control.py ← app/{logger, store}`：不依赖 security，避免循环；
- `gateway/routes_tickets.py` 对 `access_control` 使用**函数内局部 import**，刻意打断环；
- `kms/security.py → gateway/state.py`：state 仅依赖 config，是叶子节点。
