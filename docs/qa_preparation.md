## 一、架构设计类（5 题）

### Q1：为什么要把权限模型从多角色简化为单一"员工"？

**答**：原系统的多角色体系（安全管理员、审计员、文档管理员等）带来三个问题：
1. **权限判定复杂**：需要同时判断角色、职责、提权状态，逻辑分散在多处
2. **审计困难**：同一操作不同角色有不同路径，审计追踪困难
3. **安全隐患**：临时提权机制可能被滥用

简化后，权限判定仅依赖安全职级 + 部门两个维度，BLP 规则清晰、审计链路统一。

### Q2：BLP 模型中的"不下写"在实际业务中意味着什么？

**答**："不下写"意味着高职级员工不能直接修改低密级文档。例如 L3（机密）职级的员工不能直接修改 L0（公开）文档。

这看起来反直觉，但逻辑是：如果高职级可以随意修改低密级文档，可能导致信息降级泄露。比如机密级员工把公开文档改为包含机密信息的内容，但文档密级仍是公开，导致泄密。

实际业务中，高职级员工可以通过工单申请修改，由满足条件的审批人审批后执行。

### Q3：为什么选择两段式工单而不是三段式？

**答**：三段式（申请 → 审批 → 执行）需要一个独立的"执行人"角色。但在我们的场景中：
1. 审批通过后，系统可以自动执行入库/更新/删除操作
2. 不需要人工执行环节
3. 减少一个角色，简化流程

所以采用两段式：审批通过即执行，审批驳回即终止。

### Q4：API 网关为什么用中间件而不是独立的网关服务？

**答**：当前阶段系统规模不需要独立网关（如 Kong/APISIX）。FastAPI 中间件可以实现：
1. 速率限制（滑动窗口 60次/分钟）
2. 全链路审计日志
3. 请求 ID 注入

如果未来需要多服务编排、协议转换等能力，可以平滑迁移到独立网关。

### Q5：系统如何保证高可用？

**答**：
1. **HR 同步失败兜底**：使用旧缓存数据，不阻断业务
2. **幂等建表**：所有 DDL 都是 `CREATE TABLE IF NOT EXISTS`，重启不报错
3. **文档锁超时释放**：工单超时自动驳回并释放锁，防止死锁
4. **无状态服务**：FastAPI 应用本身无状态，可以水平扩展

## 二、数据安全类（5 题）

### Q6：HR 数据同步的安全性如何保证？

**答**：
1. **单向只读**：KMS 只能从 HR 系统读取，不能反向写入
2. **upsert 策略**：以工号为唯一键，HR 数据覆盖更新
3. **KMS 不可修改人事主数据**：系统不提供修改员工部门/职级的接口
4. **同步失败兜底**：失败时使用旧缓存，不影响已登录用户的正常使用

### Q7：审计日志如何防止篡改？

**答**：
1. **独立存储**：审计日志表（kms_audit_logs）独立于业务表
2. **只写不更新**：系统只提供 INSERT 接口，不提供 UPDATE/DELETE
3. **分级脱敏**：不同职级看到不同详细程度，但底层数据完整
4. **哈希链**：工单提交/审批都有哈希校验，防止 payload 被篡改

### Q8：文档悲观锁如果死锁了怎么办？

**答**：
1. **超时机制**：每个工单有差异化超时（72h/48h/24h），超时自动驳回并释放锁
2. **强制释放**：`force_release_lock(doc_id)` 接口用于运维场景
3. **唯一索引**：`UNIQUE KEY uk_doc_id (doc_id)` 保证同一时刻只有一个锁
4. **定时扫描**：`check_timeout_tickets()` 每分钟扫描一次

### Q9：RAG 检索如何避免召回过期内容？

**答**：文档更新时，旧版本的 chunk 不是删除，而是移入**归档向量库**（kms_archive_chunks）。RAG 检索只从主向量库（chunks 表）召回，自动排除已归档切片。

这样既保证了检索不会召回冲突内容，又保留了历史数据用于审计合规。

### Q10：JWT Token 的安全性如何保证？

**答**：
1. **HS256 签名**：使用密钥签名，防止伪造
2. **密码散列**：PBKDF2-HMAC-SHA256，带随机盐
3. **Token 过期**：设置合理过期时间
4. **HTTPS**：生产环境强制 HTTPS 传输

## 三、业务逻辑类（5 题）

### Q11：工单自动匹配审批人的逻辑是什么？

**答**：`auto_route_ticket(doc_level, doc_dept)` 的筛选条件：
1. `security_level >= doc_level`：满足 BLP 读规则（审批人需要能读到文档）
2. `department == doc_dept`：同部门（文档归属部门）
3. `is_active == 1`：在职员工
4. `id != applicant_id`：不能自己审批自己

如果候选人为空（比如部门内没有满足职级的人），工单会创建但标记为"无可用审批人"，需要 L2+ 管理员介入。

### Q12：如果同一个文档有多人同时上传怎么办？

**答**：文档悲观锁保证同一 doc_id 同一时刻只有一条在途变更工单。

第一个上传请求获取锁，后续请求被拒绝（"文档已在途变更，请等待工单办结"）。工单办结后锁释放，才能发起新的变更。

### Q13：工单超时后文件怎么处理？

**答**：
1. 工单状态变为 `timeout`
2. 文档锁释放
3. 暂存的文件在 staging 目录保留一段时间（可配置），超期后清理
4. 通知申请人："工单已超时自动驳回"

### Q14：安全职级 L0-L3 是谁定义的？KMS 能修改吗？

**答**：安全职级由 **HR 系统**定义，是人事主数据的一部分。KMS 只能只读引用，不能修改。

如果需要调整员工职级，必须在 HR 系统中操作，然后通过同步更新到 KMS。

### Q15：文档的“额外开放部门”是什么场景？

**答**：默认情况下，文档只能被同部门员工读取。但有些文档需要跨部门共享，比如：
- 技术文档需要给产品部门看
- 财务制度需要给所有部门看

这时可以设置 `extra_departments` 字段（JSON 数组），列出额外开放的部门。读规则变为：`emp_dept == doc_dept OR emp_dept IN extra_departments`。

写规则仍然要求严格同部门。

### Q16：工号为什么采用 2026+四位数字的格式？

**答**：这是参照银联商务企业实践的工号编码规则：
1. **前缀 2026**：代表入职年份，便于识别员工资历
2. **四位数字**：从 0000 开始顺序编号，简单明了
3. **初始密码=工号**：便于演示和登录，实际生产中会强制首次登录修改密码

这种设计让评委和演示用户可以快速登录系统体验，不需要记忆复杂密码。

## 四、技术实现类（5 题）

### Q17：为什么用 FAISS 而不是 Milvus/Pinecone？

**答**：
1. **轻量级**：FAISS 是 Facebook 开源的本地向量库，无需独立部署
2. **性能足够**：当前文档规模（万级）FAISS 完全胜任
3. **归档隔离**：我们可以用 MySQL 表管理归档 chunk，FAISS 只存活跃向量
4. **未来扩展**：如果规模增长到百万级，可以迁移到 Milvus

### Q18：Embedding 模型用的什么？为什么？

**答**：使用 **BGE-M3**（1024 维），原因：
1. 中文效果好（BAAI 训练）
2. 支持多语言
3. 1024 维在精度和性能间平衡
4. 开源免费

### Q19：分块策略是怎样的？

**答**：
1. 文本类文档按段落/句子分块，chunk_size=500 字，overlap=50 字
2. 表格类文档按行分块
3. PDF 先提取文本再分块
4. 每个 chunk 记录 content_hash，用于去重和归档

### Q20：幂等建表是怎么实现的？

**答**：所有 DDL 使用 `CREATE TABLE IF NOT EXISTS`，应用启动时自动建表。

对于字段扩展（如给 kms_users 增加 department 字段），使用 `ALTER TABLE ADD COLUMN`，捕获 `Duplicate column` 异常并跳过。

这样应用重启不会报错，Schema 演进平滑。

### Q21：如果 MySQL 不可用了怎么办？

**答**：
1. **降级策略**：`ensure_kms_acl_tables()` 捕获异常返回 False，应用仍可启动（只读模式）
2. **HR 同步兜底**：使用旧缓存数据
3. **审计日志缓冲**：如果审计表不可写，日志暂存内存队列，MySQL 恢复后补写
4. **监控告警**：MySQL 不可用触发告警，运维介入

## 五、加分题（备用）

### 如果让你重新设计，你会改进什么？

1. **引入事件驱动**：工单状态变更通过消息队列（如 Redis Stream）通知，解耦更彻底
2. **向量库升级**：规模增长后迁移到 Milvus，支持分布式
3. **前端框架化**：当前是原生 JS，可以迁移到 Vue/React
4. **多租户支持**：如果多个子公司共用，需要租户隔离

### 这个系统的性能瓶颈在哪里？

1. **Embedding 计算**：大批量文档上传时，Embedding 计算是瓶颈（可以用异步队列）
2. **FAISS 检索**：百万级 chunk 后检索延迟增加（可以分片+IVF 索引）
3. **MySQL 写入**：高并发工单场景（可以引入 Redis 缓存热点数据）
