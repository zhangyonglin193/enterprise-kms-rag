# 知识服务说明：权限、加工、对外服务与版本治理

> 适用对象：接手本系统的运维、应用接入方、答辩备询。
> 本文只写**已验证的行为**；凡属设计思路而尚未落地的，均显式标注「思路，未实现」。
> 端口：**6341 = 问答服务（赛题评测口）**，**6342 = 企业知识服务（KMS）**。

## 0. 角色模型：只有两类人

```python
# kms/constants.py
ROLE_EMPLOYEE = "employee"     # 唯一基础身份
# 注释原文：每个在职员工都可以发起工单，系统中不存在「管理员」角色。
```

| 身份 | 能做什么 |
|---|---|
| **员工** | 申请删除/导入/改密级、问答、浏览目录；能读什么由 BLP 决定，变更须过双人审批 |
| **运营审计** | 上述全部 **+** `/audit/*` 四个只读接口；**对业务内容不额外授权** |

**刻意没有管理员**：审批权若来自「管理员身份」，谁当管理员谁就能批一切，
审批就成了身份特权而非岗位责任。审批权改由**组织属性派生**（部门 + 安全职级），
判定入口唯一：`kms/access_control.py: approver_candidates()`。

配置里曾有的 `KMS_ADMIN_EMPLOYEES`、`KMS_EDITOR_EMPLOYEES` 已彻底移除
（含 `.env` / `.env.example` / `.env.kms` / `.env.kms.example` 与 9 个测试文件），
网关上原挂管理员身份的门闸统一改挂运营审计。

### 0.1 全员可申请，审批把关

**所有在职员工都可以申请**删除、导入、改变密级——系统里**没有「编辑员」白名单**。
准入只剩一个条件：**有归属部门**（否则无法界定"这是谁的地盘"，部门隔离与
跨部门审批校验都无从谈起）。

```python
# gateway/routes_kms.py
def editor(user: AuthUser = Depends(require_user)):
    if not user.department:
        raise HTTPException(403, "需要归属部门才能发起文档变更")
    return user
```

**必须分清"能申请"和"能通过"是两件事**：放开的是申请入口，不是执行权。
任何变更仍要走双人审批才算生效。若把它理解成"现在谁都能直接改文档"是错的。

历史上这里曾是工号白名单（`KMS_EDITOR_EMPLOYEES`），导致只有风险控制部
两人能发起变更，**其余七个部门实际是瘫的**——想维护自己部门的文档会被 403 挡住。
废弃理由与 `KMS_APPROVER_EMPLOYEES` 相同：留一个看着能授予权限、实际不生效的
配置项，比没有更容易误导运维。

## 1. 文档权限如何管理

### 1.1 两个正交维度

| 维度 | 取值 | 作用 |
|---|---|---|
| **密级** | L0 / L1 / L2 / L3 | BLP 模型：不上读、不下写 |
| **归属部门** | 具体部门 或 `*`（不限） | 部门隔离；`*` 放开的是部门维度，**不是隔离本身** |

关键点：**`*` 只放开部门维度**。L2 员工改读一篇「不限」的 L2 文档可以，
但读别部门**限定**的 L2 文档依然不行。实测对照过：同一篇文档只切归属部门字段，
异部门员工读「限定」= False，读「不限」= True。

### 1.2 单一事实源

```
列表路径  visible_documents_sql()  ┐
                                  ├─> can_read_doc()   ← 唯一的判定处
问答路径  current_contexts()       ┘
```

两条路径必须同源。否则会出现「列表看不到、问答搜得到」——那等于把权限
做成了界面装饰。`app/rag.py` 里 0 处部门引用，部门过滤全在 `current_contexts`。

### 1.3 发布的四重闸门

一篇文档要被检索到，必须同时满足：

```
status = 'published'
lifecycle_state = 'published'
publication_approved = 1      ← 双人审批产物
未过期 (expires_at)
```

**草稿不进检索。** 真正的暴露门槛是发布审批，不是上传。

### 1.4 审批人怎么来

`approver_candidates()` 同时要求：

1. 同部门，或文档归属为 `*`
2. 安全职级 ≥ 文档密级
3. **HR 涉密准入通过**：在职/试用 + 正式员工 + 已签保密承诺 + 背景审查通过
4. 排除申请人本人（A/B 分离，不能自批）

第 3 条的理由：让没有涉密资格的人去审批一篇他无权接触的文档，
形式上是双人审批，实质上是单人决定。

第 4 条与密级是**相乘而非取代**：没资格的人职级再高也不进；
有资格的人能读什么仍由 BLP 决定。

### 1.5 一个容易混淆的点

`security_level`（保密能力）与 `hr_job_grade`（职等，如 P5/M3）**是两件事**。
混为一谈会让「提拔」被误读成「提密」。

## 2. 知识如何加工

### 2.1 入库链路

```
原始文件（只读，绝不改写；临时文件统一放系统 temp）
  └─> 格式解析  pdf / docx / doc / txt / md / csv / json / xml / html / xlsx
       └─> 分块     CHUNK_SIZE=300, CHUNK_OVERLAP=80
            └─> 向量化  BAAI/bge-m3, 1024 维
                 ├─> FAISS（向量检索）
                 └─> BM25（关键词检索）
                      └─> MySQL chunks 表 + documents 治理元数据
```

**图片 OCR 已停用**。原「截图/图片内容作答」规则与数字规则冲突、曾引发回归，
故长期停用；若需重启，必须连同数字规则整条回归，不要只改一处。

### 2.2 检索链路（6341 问答）

```
query
 └─> embed(query)
      └─> FAISS 检索 TOP_K_RETRIEVE=30
           └─> chunk_cache 命中（分块文本**已预载内存**，零 MySQL 查询）
                └─> rerank 重排
                     └─> 组装上下文 MAX_CONTEXT_CHARS=4000
                          └─> 两段式生成
```

**分块文本预载内存**是性能的关键：单次请求链路里没有 MySQL 查询。

### 2.3 两段式生成

1. **抽取步**：只允许从参考资料逐字抄写原文句子，禁止概括/改写/合并——
   防小模型脱上下文改写与幻觉。
2. **答案步**：基于抄写出来的句子作答。

### 2.4 冷启动

启动时三段预热：Embedding → LLM（max_tokens=1）→ Reranker（top_n=1）。
硅基流动 MaaS 有冷启动，**第一问慢是正常的**，预热完再计时才准。

### 2.5 两侧参数差异

| 参数 | 问答(6341) | KMS(6342) |
|---|---|---|
| TOP_K_RETRIEVE | 30 | 20 |
| MAX_CONTEXT_CHARS | 4000 | 3000 |
| ENABLE_TWO_STAGE | 0 | 未设 |

分块与向量参数两侧**完全相同**（300/80、bge-m3、1024 维）。

## 3. 如何给不同的应用提供服务

### 3.1 身份类型

| 身份 | 标识 | 用途 |
|---|---|---|
| **员工** | JWT（工号 + 密码登录） | 内部使用 |
| **应用** | API Key（app_id） | 外部系统接入 |

MCP 工具普遍允许「应用身份 或 运营审计」调用，例如指标工具：
`if app_id is None and not identity.is_auditor(): 拒绝`。

### 3.2 每个应用能看什么

应用绑定（`bind` / `applications` / `create_application` / `update_application` /
`rotate_application`）现在归**运营审计**管辖。原挂管理员身份，随角色模型
统一迁移。**接口本身保留**——它们是对外服务的入口。

应用的可读范围同样受 BLP 约束：密级与部门隔离对应用身份一视同仁，
不存在「应用是特权身份」这回事。

### 3.3 出网与限流

- `GW_MODEL_EGRESS_ALLOWED`：控制是否允许经网关调用外部模型。初始 `0`，
  批准后才改 `1`。
- 限流维度：按来源 IP、按嵌入应用、按 MCP 员工工号，三套独立配额。
- `/metrics` 仅运营审计可读——避免向外部暴露调用画像。

### 3.4 问答接口契约（赛题规范，勿改）

```
POST /chat
请求: {"question": "xxx"}          （同时兼容 form-data 与 ?question=）
响应: {"answer": "xxx"}
```

**只返回 answer，不带引用来源。** 准确率打分需对照参考答案人工比对。

## 4. 文档更新与版本冲突：解决思路

> 本节为**设计思路**，标注了哪些已实现、哪些没有。不要把它当成已落地功能读。

### 4.1 已实现的四道防线

**① 一致性校验（服务拒绝带病启动）**

启动时比对 FAISS `ntotal` 与 MySQL `chunks` 行数，不一致即拒启。
这比让服务跑在脏数据上安全——脏数据不会报错，只会静默给出错答案。

运营审计可直接查看：

```
GET /kms/api/audit/ingest-status
  → faiss_total / chunks_total / faiss_mysql_consistent
```

**② 重建必须停服**

入库脚本（`seed_kms_demo.py` / `reingest_all.py`）要求先停 6341 与 6342，
避免 FAISS 文件争用与缓存不一致。并发写 FAISS 文件的后果不可预期。

**③ 孤儿数据清理**

删文档必须连带清理 `kms_doc_levels` 等外键关联表。只删 `documents`
会留下悬空引用——实测中就遇到过 `kms_policy_requests` 外键挂着已删文档。

**④ 可回退备份**

重入库前全库导出 JSON（`data/pre_reingest_kms.json`）+ FAISS 索引副本。
**禁止**用「删除较大 ID 的 chunks」来修复不一致——那是掩盖问题。

### 4.2 思路，未实现

**版本冲突**：当前模型是「重新上传即替换」，没有多版本共存与 diff。
若要支持，需要：文档版本号 + chunk 关联版本 + 检索时按版本过滤。
代价是检索复杂度上升，且历史版本同样占向量空间。

**入库运行明细**：目前只有状态总览（文档数/分块数/一致性），
没有「哪次入库、哪篇失败、耗时多久」。要做需新建 `kms_ingest_runs` 表
并在入库脚本埋点，且历史入库补不回来。**刻意没做伪指标。**

**并发编辑**：两人同时改一篇文档，当前无锁。若要支持，可在
`documents` 加乐观锁版本列，提交时比对。
