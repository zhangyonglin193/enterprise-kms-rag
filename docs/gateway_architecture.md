# 企业知识治理与 RAG 升级架构

版本：2.0，2026-10-15。本文与 `gateway_api_reference.md`、`../DEPLOY.md`、`enterprise_delivery.md` 共同构成当前交付基线。其他设计文档为历史材料，不代表当前注册路由。

## 1. 定位与验收边界

本项目从竞赛问答工具升级为“评测服务独立 + 企业知识治理 + 办公渠道适配”的单机受控试点实现。交付包含代码、离线回归、部署脚本和接口契约；不等于已经完成甲方生产验收、平台联调或金融监管认证。

金融安全优先于功能覆盖：已有安全问题的旧入口先隔离，不能以“保留原逻辑”为由继续放行。主业务评测接口保留 `POST :6341/chat` 的 `question → answer` 契约，但启动时数据库/索引异常改为拒绝，不再自动删除数据修复。

## 2. 总体架构与信任边界

```text
组委会评测端 ───────────→ QA :6341（唯一对外暴露的主业务入口）
                              ├─ 竞赛专用 MySQL 数据库
                              └─ 竞赛 FAISS / 原始公开文档 / 缓存

办公浏览器 ──SSH隧道/批准内网──→ KMS :6342（默认 127.0.0.1）
嵌入方页面 → 宿主BFF :6343 ───→ /gw/api/v1/embed/*
飞书/企微 → 已批准HTTPS接入设施 → /gw/api/v1/bots/*
                              │
                  EnterpriseBoundary：审计、限流、请求限制
                              │
                    平台真实性 / 应用身份 / 员工身份
                              │
                  文档治理和统一知识服务 gateway/service.py
                              │
         本地向量+BM25 → RRF → 实时权限过滤 → Rerank → 再授权
                              │
                    经批准模型生成 → 输出前复核
                              │
                         完成审计后返回
                              ├─ 企业独立 MySQL / FAISS / 上传目录
                              ├─ SQLite：任务、回执、JWT撤销
                              └─ JSONL强制审计 + MySQL查询副本
```

1. 6341 只使用经批准的竞赛公开语料，不存放企业内部资料。免员工鉴权的评测入口不能与 KMS 共用任何知识数据目录或数据库。
2. KMS、网关、机器人回调均在同一个 6342 进程内；不是再起一个占用 6341 的网关。6342 可调整至 6350，6343 是可选 BFF，6344～6350 默认不启动服务。
3. 不自动新建 80/443/8000/8080 等监听器。若办公平台无法访问批准入口，平台回调联调即受阻，不绕开端口限制架设公网隧道。
4. MySQL 是既有基础设施依赖，连接其获批端口不等于本项目新增监听服务。FAISS 与 SQLite 无网络端口。
5. 应用分离不是 OS 强隔离：同一系统账号仍可能读取两套数据。真实金融环境应分账号/文件 ACL/数据库授权，必要时分主机。

## 3. 保留、整改与隔离清单

| 原有设计 | 本次处置 | 理由与影响 |
|---|---|---|
| FastAPI 分层；MySQL 与 FAISS 分工 | 保留 | 低资源部署、职责明确，适合竞赛与单机验证 |
| 向量+BM25、RRF、复杂问题召回、Rerank | 保留并增加企业过滤器 | 保留准确率路径；企业路径不会先把未授权片段交给 Rerank |
| 文档哈希、分块/页码元数据、来源展示 | 保留 | 支持防重复与可追溯回答，不把哈希称作不可篡改存证 |
| 评测答案缓存 | 仅评测使用 | 企业路径不共用缓存或旧会话，防止撤权后答案复用 |
| KMS 重复挂载免鉴权 `/chat` | 移除 | 防止绕过企业鉴权；6341 契约保持 |
| API Key 映射高密级虚拟员工 | 企业入口不再使用 | Key 标识应用而非员工；无 JWT 最多读已发布 L0 |
| 缺分类/缺部门默认公开 | 改为拒绝 | 历史数据不能自动成为公开资产 |
| 高安全密级等于管理权限 | 改为职责名单 + 文档属性约束 | 管理员不因管理身份自动获得所有知识 |
| 草稿或双生命周期状态不一致仍可检索 | 发布标记及双状态校验 | 只有双人批准的 published 内容可用于回答 |
| JWT 登出仅前端删除 | 服务端持久撤销 | 改密撤销已有令牌，长问答放行前再核验 |
| 回调 ACK 后才创建内存任务 | 事务入队后 ACK | 重启后可恢复，不把 BackgroundTasks 当可靠队列 |
| 数据数量不一致自动删 chunks | 删除修复行为 | 启动校验实际 ID 集合、重复 ID、孤立分块；恢复一致快照 |
| 部署清库/覆盖配置/模糊进程终止 | 非破坏安装、固定 socket | 不抢占其他服务，不把进程创建当作启动成功 |
| 旧工单、覆盖版本、SSE、历史、推荐分析 | 源码保留但 HTTP 隔离 | 原权限依赖、状态同步和写入链路未经安全迁移，不能宣称功能全部保留 |
| HTTP HR 手工上报任意员工密级 | 不注册写入口 | 防止伪造主数据自助提权；试点使用批准清单离线初始化 |

## 4. 身份与权限模型

### 4.1 身份与职责

- 员工主数据：工号、姓名、部门、在职状态、安全密级来自经复核的人事来源。目录同步为可插拔适配器（见 4.4）：默认内置种子，可切换标准 LDAP 或微软 AD（只读账号，凭据仅经 `.env` 注入）。
- 密级：L0 公开、L1 秘密、L2 机密、L3 绝密，是项目内部标签，不自动对应国家秘密法定定密。
- 员工：所有在职员工均可申请删除/导入/改变密级；**无编辑员白名单**，把关靠双人审批而非身份授权。
- 审批人：不按名单配置，由「同部门或不限 + 安全职级 ≥ 文档密级 + HR 涉密准入 + 排除申请人本人」派生，见 `access_control.approver_candidates`。`KMS_APPROVER_EMPLOYEES` 已废弃。
- 运营审计：`KMS_AUDITOR_EMPLOYEES`，只读监控 `/audit/*` 与网关管理入口；不自动拥有内容写入权。
- 系统中**不存在「管理员」角色**（`kms/constants.py`）。审批权来自组织属性而非身份特权——否则「谁当管理员谁就能批一切」，审批就成了身份特权而非岗位责任。
- 申请人不得审批自己的申请（A/B 分离）；其余职责组合仍需甲方组织制度约束。不能称为已经全面实现所有“三权分立”要求。

JWT 的签名、issuer、audience、有效期、撤销状态校验后，每次查当前员工记录；不信任客户端提交的姓名、部门、密级。新密码 PBKDF2 600000 次；HTTP 改密要求 12～128 位并包含字母数字。登录失败限速与入口限流叠加。生产需进一步接入 MFA、账号全生命周期和密钥托管。

### 4.2 文档可读条件

对企业问答、文档目录及正文读取，必须同时满足：

```text
已登记 L0～L3 分类
AND 应用最小密级 <= 文档密级 <= min(应用最大密级, 员工当前密级)
AND publication_approved = 1
AND status = lifecycle_state = published
AND expires_at 为空或尚未到期
AND [L0 OR (有效员工 AND 非空部门 AND 命中归属/额外开放部门)]
```

员工工作台无应用范围限制，但仍受员工及文档属性限制。仅 Key 的应用没有内部员工身份，其可读上限固定为 L0；如果应用最小密级大于零则无可读知识。无效 JWT 不降级为匿名。机器人未绑定或员工停用直接拒绝。

治理读取与普通读取不同：维护/审批人员可以查看本部门、本人可管理密级的草稿；未分类文档仅本部门 L3 可治理。空归属旧文档不进入治理列表，必须在维护窗口依据批准资产清单补正，不能由任意部门抢领。

### 4.3 双人发布

```text
L3维护员上传 → 本部门 L3 draft
      ↓ 维护员提出策略（密级、部门、额外开放部门、状态、理由）
请求 pending + 文档快照哈希
      ↓ 独立同部门审批员查看原文及策略
锁文档 → 锁申请 → 检查非自批、双方职责/密级、快照、有效期
      ↓ 一个 MySQL 事务
更新密级 + 双状态 + 发布审批标记 + 审批人/结果
```

降密不是直接编辑等级，而是审批动作。申请人不能批准自己的请求；审批员与维护员名单互斥。已有 pending 请求拒绝重复创建；状态冲突返回 409。当前不支持待审批申请撤销/过期定时关闭、跨部门移交或完整版本树。

### 4.4 统一登录与目录适配（可插拔）

对标 IBM 等企业 KMS：知识问答系统以 Relying Party 身份接入企业统一身份平台，人员/组织主数据来自目录服务。两者均以**适配器 + 配置开关**实现，业务代码不感知具体实现，本系统不维护人员主数据。

统一登录（OIDC / OAuth2）——`KMS_OIDC_PROVIDER`：

- `builtin`：内置模拟 IdP 授权码流（`/kms/api/auth/sso/authorize → login-page → login-submit → token`），本地/竞赛演示用。
- `external`：对接外部 OI 平台。`POST /kms/api/auth/sso/exchange` 接收外部 `id_token`，经 JWKS（RS256）验签并校验 `iss`/`aud`/`exp`，按 `KMS_OIDC_EMPLOYEE_CLAIM`（默认 `emp`）映射内部工号，命中在职员工后签发 KMS JWT；审计动作 `sso_external_exchange`。验签依赖惰性可选 `PyJWT`+`cryptography`，未安装时明确报错，不静默降级。

目录同步（LDAP / AD）——`KMS_DIRECTORY_SOURCE`：

- `seed`：内置组织种子 + 可选 `KMS_LDAP_SEED_JSON` 模拟目录返回（离线评测）。
- `ldap` / `ad`：只读绑定账号连接标准 LDAP / 微软 AD（AD 建议 LDAPS 636），按 `KMS_LDAP_*_FILTER/_ATTR` 拉取 OU 与员工，映射到 `kms_org_nodes` 与 `kms_users`（只读镜像）；惰性依赖 `ldap3`，未安装时明确报错。
- 同步流程：`upsert_org_nodes`（组织树，重算 `parent_id`/`org_path`/`org_level`）→ `hr_sync.sync_employees`（行哈希增量对账）→ `backfill_user_orgs`（回填用户组织字段）。ldap/ad 模式必填项由 `validate_ports()` 在启动阶段拦截。

每次问答请求都会注入组织上下文（`org_path`/`org_node_id`/`manager_employee_no`/可见组织范围），供回答优先取材于用户所属组织范围；权限判定叠加组织层级继承（上级可见下级文档）。

## 5. 企业问答的数据流

1. 入站强制审计；身份验证和限流；验证问题长度。
2. 只有 `GW_MODEL_EGRESS_ALLOWED=1` 才允许企业模型调用。Embedding 会接收问题本身，因此开关覆盖问题及资料出域，不是只保护分块正文。
3. 本地 FAISS/BM25 候选融合。进程会接触本地候选 ID/文本，但在向 Rerank 发送正文之前，按当前 MySQL 权限过滤并覆盖内存中的旧正文。
4. Rerank 后重新获取授权资料，再构造提示词；无可读资料拒答，不使用模型自由发挥代替依据。
5. 提示词标明引用资料是不可信数据，不执行其中指令；无支付、审批、链上交易执行工具。
6. 输出前检查来源权限与文本，变化返回 409；员工和应用状态再核验。
7. 生成绑定当前主体的回执；HTTP 响应完整缓冲，完成审计后返回。

权限检查与网络发送之间仍存在分布式系统常见的并发时间窗口。已经发送给批准模型的内容不能通过后续撤销“收回”；不能宣称数学意义的零竞态或提示注入完全免疫。

## 6. 审计、任务及存储

| 存储 | 内容及边界 |
|---|---|
| `documents` / `chunks` | 原文元数据、分块、FAISS ID；企业与竞赛独立数据库 |
| `kms_doc_levels` | 文档密级；缺记录拒绝，不补公开 |
| `kms_users` / `kms_apps` | 员工镜像、应用 Key 哈希；不把 Key 明文写入日志 |
| `kms_policy_requests` | 申请、理由、快照、申请/审批人、结果和请求 ID |
| `kms_gw_bot_bindings` | 平台 ID → 员工工号；变更需要管理员授权 |
| `kms_gw_audit` | 查询副本，不作为唯一持久审计凭证 |
| JSONL | request_started/request_finished、worker 事件；追加并 fsync，失败关闭 |
| SQLite `jobs` | 唯一事件键、状态、尝试次数、租约、请求号；任务终态清空问题正文 |
| SQLite `receipts` | message_id、应用/员工主体、反馈；不保存答案全文 |
| SQLite 撤销表 | jti 到期信息、员工级撤销时间 |
| `kms_org_nodes` | 组织架构树（部门/团队、负责人、`org_path`）；供层级继承与上下文注入 |
| `kms_rec_interactions` | 推荐交互行为（`chat_source`/`view`/`feedback`、权重、`message_id`）；反馈可回溯来源 |

机器人队列：最多 1000 个活跃任务；最多 3 次尝试；失败间隔 30×尝试次数秒；在途租约 1800 秒；终态去重键清理阈值 7 天。反馈清理阈值 30 天。清理是业务触发，并非严格定时删除；真实留存期限由甲方审批。

队列提供持久去重与有界重试，不提供 exactly-once。飞书请求 UUID、企微重复检查只是辅助；发送成功但确认前崩溃仍可能重复。平台未接受消息不保证最终送达，需审计告警与人工处置。

审计不记录 Key、JWT、密码、问题/答案全文、回调查询串。文件写成功后数据库副本失败只告警。双写不是 WORM，也没有数字签名链、集中补录和防管理员篡改证明。业务事务可能已提交而完成审计失败，此时 HTTP 503，必须按请求号核对状态再重试。

## 7. 可靠性及落地限制

- 当前仅单 KMS worker，SQLite 不放共享 NFS；不能直接改为多副本部署。扩容需消息代理、共享幂等存储、分布式限流及索引发布机制。
- 上传限制文件类型、大小、串行和不覆盖；尚无文件杀毒、解析沙箱、压缩炸弹检测、MySQL/FAISS 跨存储原子发布。仅允许受控员工提交预审文件。
- 启动校验 ID 集合及分块归属，不校验向量语义或完整内容校验和。更换 Embedding 模型必须重建匹配索引，不能只比较维度。
- 发布策略数据库事务已实现；真实 MySQL 隔离级别、行锁并发、故障恢复仍需集成验收。
- API 64 KiB 请求限制、上传 10 MiB 文件/11 MiB 请求、16 MiB 响应缓冲是单请求上限；需要压测并设置代理超时、连接数和磁盘配额。
- `/readyz` 表示初始化完成，不表示当前模型/平台实时健康。启动超时、审计满盘、任务积压必须有外部监控。
- TLS、IAM、DLP、备份加密、WORM、渗透测试和监管评估属于生产准入，不因文档写出名称就算已实现。

## 8. 商用演进顺序

1. 受控试点：批准数据、分库分账号、双人治理、办公平台测试应用、离线与真实环境验收。
2. 甲方集成：SSO/MFA、可信 HR 同步、统一网关、模型准入与数据脱敏、集中审计。
3. 生产可靠性：隔离解析服务、病毒扫描、持久入库任务、版本化索引发布、备份恢复及容量测试。
4. 企业扩展：多租户/商户级隔离、API 产品管理、法律保留、跨部门知识流转、指标与质量闭环。

各阶段均需业务、合规、安全、运维共同签署准入条件；本版不承诺未经测试的准确率、并发量或 SLA。

## 9. 权限隔离定向推荐

`GET /kms/api/recommendations`（需员工 JWT）在**不放大权限**的前提下产出「可能相关且本人有权访问」的文档，服务定向推荐与知识触达。

- 四路策略加权融合（权重经 `.env` 配置）：组织画像（本部门/组织层级范围）、语义相似（向量检索）、协同过滤（item-item 共现，交互不足时冷启动降权）、热度（半衰期衰减；无交互时以最新发布兜底）。
- **权限硬过滤**：融合后的候选逐条复用 `gateway.service.allowed()`（密级∩部门∩组织继承∩状态∩审批∩有效期），未授权文档一律剔除，不存在「推荐即泄漏」旁路。
- 行为埋点：企业问答命中的来源写 `chat_source`，文档详情读取写 `view`，用户反馈写 `feedback`（按 `message_id` 回溯问答来源）；埋点全部容错，失败不影响主业务。
- 可回滚：`KMS_REC_ENABLED=0` 关闭推荐并返回空列表，不影响问答与权限主链路。
- 边界：推荐为辅助触达，不改变授权判定；本版未做在线 A/B 与效果闭环，指标与冷启动优化属商用演进项。
